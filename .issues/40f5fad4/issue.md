md2todo.py fence detection currently treats an unclosed fence as swallowing everything after it to EOF, silently. The repro file codgent_2e4c42b202c1471bae09511de7fd77a4ee138c9d_TODO.md had 13 fence markers; under the old code line 125 (inline fence) opened a fence that cascaded pairing 125->659, 662->774, 814->840, 844->900, 941->946, leaving 952 unclosed (odd marker count), swallowing 82 items. The fixed inline-fence rule (commit 5c47461) makes the pairing balanced, but an unclosed fence is still a silent data error: there is no valid interpretation of the rest of the file once a fence swallows it. Proposed: md2todo.py should fail hard during the scan/parse phase (before build_plan) when a fence is opened and never closed, with the line number of the fence opener in the error. Rationale: an unclosed fence is almost certainly a typo in the source file; the fix is to close the fence in the source file, not to make the importer tolerant. Test cases to add: (1) unbalanced fence, not same-line: a file with an unclosed fence opener (not inline) plus checkbox items after it - import must fail with the line number of the opener; (2) unbalanced fence, no items after: a file that legitimately ends with an unterminated code block (e.g. a truncated log) but no items after it - import must also fail (the fence is broken as a markdown document, and the notes content is still misattributed); (3) balanced fence: current behavior unchanged, imports fine.
